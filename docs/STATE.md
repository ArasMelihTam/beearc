### ❌ Hive condition score — BUILT, THEN REMOVED THE SAME DAY (2026-08-12)

**Do not rebuild this without the user asking for it.**

A weighted, time-decaying condition model (`src/logic/condition.ts`, 35 tests) briefly existed: Bayesian queenrightness so that a missed queen was never read as queenlessness, per-factor half-lives, importance weights, disease as a multiplier rather than an average, a clamped least-squares trend term, confidence blending, a red→amber→green meter, a compact list badge, and a "show your work" breakdown screen.

**The user removed it: "I believe we need to remove this system and just state the days of the last inspection and have the name and people can see the details of the inspection, I prefer it to be kept simple."** They had also asked, one message earlier, whether it should go because it felt unpredictable. I recommended keeping it and judging it against real colonies first (it had never run on a phone); they reaffirmed, so it was removed in full — no dead code, no dangling i18n, no leftover tokens. Recoverable from git history if it is ever wanted back.

What survived from that round, and why it is worth remembering:

- The user was **right** that findings were not proportionate. A beetle was costing ~10% of the score, about half of what a ruined brood pattern cost. If any scoring is ever attempted again: **beetle < wax moth < bad brood < starvation and heavy varroa < disease.**
- The principle they insisted on stands regardless of any algorithm: **not seeing the queen or eggs does not mean they are absent** — the beekeeper may simply have missed them. Nothing in the app may treat "not seen" as "not there". Rule R3 already handles this correctly by scheduling a recheck rather than declaring anything.
- **Deleted with it:** `src/logic/condition.ts` + its tests, `src/components/ConditionMeter.tsx`, `app/hives/[id]/condition.tsx`, `src/theme/conditionColor.ts`, the `conditionLow/Mid/High` theme tokens, and the `condition.*` i18n block in both languages. `recencyColor` was rescued into `src/theme/recencyColor.ts` because the recency shading was a **separate** user request that stays.

### FIXED 2026-08-13 — "Something went wrong opening the database" (migration 0005 re-ran) — committed as `03e7453`

The app would not open at all. The error screen read: *Failed to run the query 'ALTER TABLE `inspections` ADD `other_insects_seen` integer;'*

**Cause.** Migration 0005 was regenerated from scratch on 2026-08-12 on the belief that it had never run on a device. It had. Drizzle decides what to apply purely by timestamp — it reads the single newest row of `__drizzle_migrations` and re-runs every journal entry dated after it (`sqlite-core/dialect.cjs:679`). The regenerated file carries a later `when` than the one the phone had recorded, so the phone re-ran the ALTER, SQLite refused with `duplicate column name`, the whole migration transaction rolled back, and `useMigrations` reported failure forever. Every relaunch repeated it.

**Fix — `repairMigrationLedger()` in `src/db/repair.ts`.** If `inspections.other_insects_seen` already exists, the migration is done in substance, so the repair records it in the ledger and drizzle skips it. Called from `client.ts` at import time, which is what guarantees it lands before `useMigrations`' effect — a `useEffect` in DbProvider would run *after* it and be useless. No-op on a fresh install, on a device without the column, and on a device already repaired; wrapped in try/catch so a failed repair can never itself block startup. **Data is preserved** — the alternative was deleting the app and losing the user's real apiary and hives (M7 backup does not exist yet).

Verified against real SQLite (`python3`, script kept out of the repo): the pre-repair state reproduces the exact error the user saw; post-repair the chain applies with nothing re-run and an existing hive row survives; a fresh database is untouched by the repair and builds 0000→0005 normally, without the dropped `pests_note` column; running the repair twice writes one ledger row.

**Left behind on the device:** the `inspections.pests_note` column from the withdrawn old 0005. It is nullable and undeclared in `schema.ts`, so nothing reads or writes it — inert. Not worth a migration on one dev phone.

**The rule this cost us:** *a migration is frozen the moment it runs ANYWHERE, including on the dev phone.* After that, correct it with a new migration, never by regenerating. The old note said regenerating was "only safe because it had never been applied on a device" — the assumption, not the reasoning, was wrong.

**Also fixed:** the DB error screen showed drizzle's wrapper message (which query failed) but not `error.cause` (why). `duplicate column name: other_insects_seen` was invisible. `errorDetail()` in `DbProvider.tsx` now appends the cause — this text is the only diagnostic a user standing in a field can send back.

## Watch for this on device (M5e, unverifiable off-device)

`SummaryRow` puts a horizontal `ScrollView` **inside** the row's `TouchableOpacity`, with a second `TouchableOpacity` around the text so a tap works from inside the scroll view too. Nested touchables and scroll views are exactly where React Native gesture handling surprises you, and no amount of `tsc` or Jest proves it. If a tap on the value feels dead, or the row opens while the finger is dragging, the fix is to stop nesting: take the press off the outer row and give it to the icon, the label and the chevron individually, leaving the scroll view purely for reading.
